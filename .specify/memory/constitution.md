# Saintber.Forge Hub 憲章

> **狀態：Active（v1.0.0），2026-10-06 由使用者批准。** 本憲章具約束力。

本憲章只定義 **Hub**（`saintber` 工具集入口）的**不可退讓的原則**。具體規範（目錄配置、版本、平台矩陣、契約格式、測試規則）放在 [Policy](../../docs/governance/policy/README.md)，不放在這裡。

各專案（`projects/<id>/`）有自己的憲章。專案憲章**可以加嚴，不得牴觸**本憲章。

## 核心原則

### I. 工具自主，Hub 與工具互不知道對方的內部

- 每個工具自己持有 install / configure / run、狀態、安裝範圍、PATH 與技術選擇。
- 工具可以被直接呼叫，也可以經由 Hub 委派；兩種方式必須走同一套實作與同一份狀態。
- Hub 只知道「工具在哪裡、怎麼呼叫」；工具只知道「收到什麼操作與參數」。
- Hub **不持有**工具的安裝狀態，也不替工具決定安裝位置或範圍。

### II. 工具必須可遷出

- 工具目錄本身是一個完整的專案：文件、治理、Spec Kit、套件定義都在其中。
- 遷出時需要處理的項目必須被明確列出；**不得**假設單靠 `git subtree split` 就能獨立。
- 工具遷出後，使用者對它的命令前綴與呼叫方式維持不變。

### III. 只透過公開契約互動

- 工具不得依賴 Hub 的內部實作，也不得載入其他工具的目錄中的程式。
- 合法的互動只有兩種：**公開的 CLI / API 契約**，以及**有版本的 Shared 套件**。
- 開發期的連結也必須遵守同一份契約，不得因為在同一個 repo 就走捷徑。

### IV. 規格唯一

- 唯一的是**同一 capability 與 requirement ID 的有效定義**。
- 有效規格以 capability 劃分，每個 capability 只有一個 owner；requirement ID 穩定、不重用。
- 進行中的工作包是**提案**，不是現況；封存的內容預設不被讀作需求。
- 有效規格只能經過**驗證後的採納**更新，不得直接以未驗證的提案取代。

### V. Policy 具約束力

`docs/governance/policy/` 中 status 為 active 的 Policy 具約束力。

- 各階段依 Policy 的 `applies-to` 讀取並檢核適用的 Policy。
- 任何違反都必須取得該 Policy 的 **owner 核准**的例外；在 plan 中記錄理由**不等於核准**。
- **代理不得自行核准例外。**
- 專案可以加嚴 Policy，不得放寬。

### VI. 設計先於實作；文件必須與事實相符

實作必須依照**已核准的設計**進行。**不得先偏離，再回頭修改文件使其合理化。**

**例行工作**（在既有授權與已核准設計的範圍內）直接進行，**不需要**為每一個新規格或工作包另外徵求批准。各工具依自己的憲章與 Policy 決定自己的流程。

只有當工作**超出既有授權與已核准設計的範圍**，需要**變更已採納的架構、放寬或變更規範（憲章 / Policy）、破壞公開契約**時，才必須**先**取得相應 owner 的核准，再依新設計實作。核准可以來自使用者**本次的明確指示**，也可以來自**既有授權**；已授權功能範圍內的工作包，**不另設逐案批准關卡**。

1. **變更提案與影響分析**：說明哪裡不足、為什麼，以及影響哪些憲章、Policy、規格、架構與 ADR。
2. **依 owner 核准**受影響的文件，或核准例外（原則 V）。核准的先後要清楚：**核准前**的提案、草稿與影響分析只是準備工作，不具約束力。**代理不得自行核准。**
3. **更新本次工作包的 spec、plan、tasks**，作為實作的設計基準。審查後的工作包 spec 可以作為實作基準，但它仍是 **pending**，不是現況，也不是有效規格。
4. **然後才實作**，並驗證。
5. **驗證完成並採納（adopt）後**，才更新有效規格與描述性文件。**有效規格不會因為設計獲得批准就提前改成現況**；它只描述已驗證的行為。

**ADR 是記錄，不是核准。** 可以在設計階段**先建立 Proposed 草稿**，作為提案與影響分析的載體；**經 owner 核准後才成為 Accepted**，核准的先後必須清楚標示。**不得**用新增 ADR 作為代理自行批准規範的捷徑。

**未經核准的偏離是缺陷**，**不是新的設計基準，也不是合法依據**（偏離本身確實是觀察到的事實，可以如實記為缺陷，但不能因此當成規範）：
- 停止該部分的交付與採納，**修正實作**。
- 要改設計，必須先走上述程序取得核准；**不得因為現有實作已經如此，就自動更新規範來配合它**。
- 實際行為可以如實記錄為缺陷，**記錄不產生合法性**。
- 一般的錯誤修正**不需要**新增 ADR；**只有變更已採納的架構或決策**才需要。

文件依性質各有**自己的正本**：
- 「現在怎麼運作」→ `docs/architecture/`（描述性；只描述**已完成**的實作，不得描述尚未實作的能力）。
- 「必須遵守什麼」→ Policy。
- 「現在的行為要求」→ 有效規格（經採納流程）。
- 「為什麼這樣決定」→ ADR。

原始設計與已採納的 ADR **不改寫**。決策被推翻時，新增 ADR，並將舊的標示為被取代（superseded）。**只有經核准的決策變更**才能標為 superseded；「已實現」或「進度」是另一回事，不得混為一談。

完成一項變更時，必須檢查：它是否讓任何描述性文件失效，以及它是否偏離了已核准的設計（POL-DOD 的完成條件）。

### VII. 誠實的狀態

- 尚未實作的能力，文件必須明確標示「尚未實作」，**不得**寫得像已經存在。
- 驗證不足的地方，必須記為已知缺口，**不得**宣稱已驗證。
- 「完成」必須有該次變更自己的驗證紀錄，**不得**以先前的結果推論。

## 治理

### 憲章與其他文件的關係

- 憲章**優先於** Policy、架構文件、ADR 與規格。衝突時，依憲章處理。
- 憲章**不描述實作細節**。目錄配置、技術版本、平台、格式等寫在 Policy 或契約文件。
- 本憲章與專案憲章衝突時，必須明確解決，**不採**「離得近的優先」悄悄裁決。

### 修訂程序

1. **提案**：說明修正原因、影響範圍與版本變更類型。可以先準備草稿與影響分析。
2. **影響評估**：檢視所有 Policy、架構文件、規格與實作是否相容。
3. **版本決策**：依下方的版本規則決定。
4. **核准**：由憲章 owner 核准，**在修訂生效、且依據它的實作開始之前**。目前 owner 是 `saintber`。代理不得自行核准。
5. **生效**：核准後才更新憲章與版本號，並在檔頭的 Sync Impact Report 記錄。
6. **傳播更新**：更新所有受影響的相依文件，包括各專案的繼承基線。

修訂的草稿在核准前處於 Draft，**不具約束力**，也**不能**作為實作的依據。

### 版本規則

語義化版本：
- **MAJOR**：移除或重新定義核心原則，產生不相容的變更。
- **MINOR**：新增原則、章節，或實質擴充治理指引。
- **PATCH**：澄清用語、修正錯字、非語義性的精煉。

### 合規檢視

- **時機**：每次重大變更交付前。
- **範圍**：新增或修改的內容是否違反本憲章。
- **產出**：列出發現的問題與修正計畫。
