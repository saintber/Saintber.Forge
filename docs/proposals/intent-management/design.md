# Intent 管理策略與 `saintber-intent` 設計

- 狀態：草案（文件設計已完成，管理規則待採納）；`saintber-intent` 技能**尚未實作**
- 類型：方案探索（`design.md`）；Hub 開發流程的文件設計
- owner：Hub（`saintber`）
- 目前決策：使用者詢問是否應有 intent 技能，以及 Intent 的保存、版本與多份需求策略；Codex 說明建議組合後，使用者回覆「那這部分還有我需要決定的嗎？如果沒有你可以交由 claude 去寫文件，你再去審閱」。本輪沒有需要人類裁決的重大分歧，採用下方「採用的預設」並文件化。決策記錄見 [ADR-0006](../../architecture/decisions/0006-intent-management-strategy.md)。
- 本次範圍：管理策略文件化（[`intent-workflow.md`](../../developer-guide/intent-workflow.md)）、本設計稿、ADR-0006、必要的導覽與流程文件對齊、舊 Intent 樣本與 proposal 範本對齊。
- 尚未實作：`saintber-intent` 技能（正本、安裝器、代理入口）、任何自動化（快照、轉換、檢查）。
- baseline-commit：`7cae618`
- 受影響的 capability：不影響有效規格
- 流程：A 直接開發（只改文件；不使用 Spec Kit，不改程式）

## 問題

1. 需求依據目前散在多處：早期 `intent.md`、正式 `docs/intent/<NNN-name>/intent.md`、使用者指示。「唯一」常被誤解為「整個 repo 只有一份」，或被誤解成必須強制版本號。
2. 需求修訂缺少一致的記錄方式：什麼要記、記什麼、來源沒有時怎麼辦，沒有共同規則，也容易出現虛構的使用者指示或 commit。
3. 多份需求並存時（拆分、承接、取代、多來源匯入同一個 change），缺少明確的關係表達，容易硬選單一來源或悄悄合併矛盾來源。
4. 正式 Intent 的「Current Effective Intent」若沒有明確結束邊界，歷史補充可能被誤讀為現行需求。
5. 目前沒有處理需求分析的技能（`saintber-design` 只讀取需求分析，不改寫它）。

## 候選策略比較

| 策略 | 做法 | 優點 | 缺點 | 結論 |
|---|---|---|---|---|
| S1 全域單一需求文件 | 整個 repo 一份 Intent | 看似簡單 | 不同問題、範圍互相干擾；無法並行；與 capability 劃分不符 | **不採用** |
| S2 強制版本號（v1／v2 副本，或 semver） | 每次修訂產生新副本與版本號 | 歷史顯式 | 與 ADR-0005 的「同一角色一份主稿」衝突；多份副本讓人誤讀現行；每改字就增版本 | **不採用**為預設 |
| S3 純 Git 歷史 | 不記錄修訂，只靠 commit | 最輕 | 未提交內容沒有歷史；缺少「為什麼」；代理難以判讀 | **不足** |
| S4 同稿迭代 + 重要修訂記錄 + 選用快照（本案） | 同稿修訂；實質改變才記日期、內容、原因、真實依據；里程碑才存全文快照 | 一份現行、保留理由、成本低 | 需要紀律；pending 需要後續補證據 | **採用** |
| S5 每範圍獨立 Intent + 明確關係 | 多份 Intent 以延伸／拆分／承接／取代連結 | 並行與追溯兼顧 | 需要維護關係表 | **採用**（與 S4 組合） |
| S6 多來源取單一全域來源 | 匯入時選一份為準 | 簡單 | 掩蓋矛盾；選錯來源 | **不採用**；改以承接範圍與來源對照 |

## 採用的預設

詳細規則的正本在 [`intent-workflow.md`](../../developer-guide/intent-workflow.md)，這裡只列結論，不複製全文：

1. **唯一**指同 owner、同問題、同範圍在當下的需求依據；不是整個 repo 一份。
2. Intent 是問題、目的、期待結果、範圍、限制、未決事項、驗收方向；**不是**正式行為 spec，也**不預先選實作方案**。
3. 早期 Intent 放 `docs/proposals/<topic>/intent.md`（選用），或單檔合併稿；同 topic 同角色唯一，合併與拆分擇一；未結案同稿迭代，不強制版本號。
4. 實質修訂（問題、目標、範圍、限制、驗收方向）才記：日期、改了什麼、為什麼、真實依據；來源沒有記錄或未提交時明確 `pending`，不虛構。
5. 正式 Intent 仍選用，保留單檔、Version Index、Current Effective Intent 的既有契約，並補：Index 記重要修訂；現行段落有明確開始與結束邊界；預設只存一份現行完整內容加修訂摘要；版本代表需求語意，可用簡單序號，不強制 semver；實質改變才換版本，非語意修正（錯字、措辭）可同號，同號即同一需求語意，精確文字以 Git commit 或快照定位；未提交版本不宣稱 Git 可還原。早期 Intent 不強制版本號。
6. 新獨立問題或能力、已確定結案或封存後的新需求另開 topic 或 change；同問題的小幅範圍調整同稿實質修訂，判斷看需求本身；多份 Intent 以延伸／拆分／承接／取代記關係。
7. 多來源匯入 change 不硬選全域唯一來源，用承接範圍與來源對照；「唯一」指現行權威，每範圍一份整合現行依據，可引用多個相容來源；同範圍來源矛盾先釐清，未裁決不合併。
8. 正式輸入承接早期範圍後，只凍結該範圍並記轉換證據。範圍已被活動 change 承接（即使沒有正式 Intent）時走 continue-change，不硬開新 topic，只有確定已結案或封存才另開。活動 change 的正式 Intent 實質修訂後：先判斷受影響的 spec／plan／驗收，不一致先釐清並更新實作基準與必要驗證，未對齊前不續做受影響實作，不以 Intent 代替 spec；工具不代做其他階段。
9. 里程碑全文快照（選用）：`docs/proposals/<topic>/history/intent-<id>.md`，`<id>` 唯一，不覆寫既有快照；唯讀；現行正本明示引用；不是第二份活動 Intent。封存腳本按整目錄封存，**不需改程式**。
10. 有效規格才是已驗證的現況；Intent 不取代它。

### 與既有決策的關係

- 與 ADR-0005 相容：同一角色一份主稿、正式 Intent 選用、凍結被承接的範圍（部分承接不整份凍結）。本設計補充**管理細節**，不重寫它。
- 與 ADR-0004 相容：轉換紀錄與修訂記錄是兩件事（前者記範圍轉成哪個 change，後者記需求理解的演變）；建立或修訂 Intent 不是轉換。
- 與 `saintber-design` 相容：它仍只處理方案探索；讀取需求分析但不改寫。本設計**不修改**它的技能、入口或程序。
- 與 POL-SPEC-001、POL-DOC-001 R5 相容：Current Effective Intent 之外的內容不被讀作需求；封存預設不讀作需求。

## `saintber-intent` 技能設計（尚未實作）

> **狀態：只有設計。** 沒有正本、安裝器與入口；`/saintber-intent`、`$saintber-intent` 目前**不可呼叫**。本節是未來實作的依據，實作時另走流程（至少 A 直接開發，並先審閱本設計），**不屬於本次範圍**。

### 定位

協助代理處理**需求分析階段**：釐清需求、判斷沿用既有稿或新 topic 或承接既有 change、維護修訂記錄並說明版本理由與來源。與 `saintber-design` 分工：

| | `saintber-intent`（設計中） | `saintber-design`（已實作） |
|---|---|---|
| 階段 | 需求分析 | 方案探索 |
| 主稿 | `intent.md`（或合併稿的需求部分） | `design.md`（或合併稿的探索部分） |
| 對另一角色 | 讀取設計稿，不改寫 | 讀取需求分析，不改寫 |

### 判斷結果（與 `saintber-design` 一致）

| 結果 | 判斷與動作 |
|---|---|
| `reuse` | 同 owner、同問題、同範圍的未結案稿；同稿修訂，必要時追加修訂記錄 |
| `new` | 新問題、獨立範圍，或已結案後的新需求；開新 topic，連回來源與關係 |
| `continue-change` | 要補充的是既有活動 change 的範圍（**有沒有正式 Intent 都適用**）；回報實際的 work package 位置，不改凍結的早期稿、不硬開新 topic、不自行建立正式輸入。有正式 Intent 且要修訂時，依版本規則提出修訂；實質修訂後先判斷受影響的候選 spec、plan 與驗收，有不一致先釐清並更新實作基準與必要驗證，基準未對齊前不續做受影響實作，不以 Intent 代替 spec；不自行執行其他階段。只有確定已結案或封存才走 `new` |
| `needs-clarification` | 身份、範圍、來源、狀態或轉換證據不明或矛盾；列出證據與待決問題，先取得答案 |

### 參數與識別

自然語言為主，可帶 `project=`、`topic=`、`from=`，**沿用 `saintber-design` 既有的專案、topic、來源識別規則**（確認專案與根目錄、不存在的專案 ID 不退回 Hub、topic 為單一名稱且不含路徑分隔或 `..`、既有 Tool 的稿放在自己的 `docs/proposals/`、standalone 不依賴別的 repo）。**不另行發明識別規則**；兩個技能的識別規則若將來有差異，以 `saintber-design` 與手冊為準並同步。

### 會做與不會做

| 會做 | 不會做 |
|---|---|
| 讀同 topic 各角色主稿、轉換紀錄、工作包、封存與有效規格，判斷結果 | 初始化 Spec Kit |
| 建立或修訂早期 `intent.md`（或合併稿的需求部分）與修訂記錄 | 代為執行 `specify`、`adopt`、`archive` 或其他階段 |
| 說明版本理由與真實依據；沒有時標 `pending` | 虛構使用者指示或 commit |
| 記錄多份 Intent 的關係與承接對照 | 自動 stage、commit、建立快照；一般建立或修訂**不產生**轉換列 |
| 實質修訂活動 change 的正式 Intent 後，提示並協助判斷受影響的候選 spec、plan 與驗收 | 代做 spec／plan／實作等其他階段；以 Intent 代替 spec |
| | 改動已結案或已被承接而凍結的範圍；修改方案探索文件 |

### 正式輸入的操作模式（僅限已確認的既有 change）

技能若列出對正式輸入的操作，**只作用於已確認存在的既有 change**（對應的 change 與工作包或封存已核對）。**修訂既有正式輸入**的模式才要求 `docs/intent/<NNN-name>/` 已存在；`continue-change` 本身在沒有正式 Intent 時也適用（只回報 work package 位置與建議，不建立檔案）。不對不存在的 change 建立正式輸入，也不代為決定 change 編號（編號仍依 [開發流程 §5.2](../../developer-guide/development-workflows.md) 手動核對）。

| 模式 | 作用 | 需求分析到正式輸入的映射與證據 |
|---|---|---|
| 讀取 | 判斷現行需求（Current Effective Intent 的明確邊界內；沒有正式 Intent 時讀記錄的需求來源） | 以轉換紀錄與承接對照表確認已承接的範圍；缺漏時先核對，不推測 |
| 修訂 | 依版本規則修訂活動 change 的**既有**正式 Intent，更新 Version Index | 版本、日期、原因、摘要與真實依據；未提交寫 `pending（未提交）`；之後依上節判斷受影響的 spec／plan／驗收 |
| 補記承接 metadata（選用） | **只在使用者明確要求記錄「已實際發生」的承接、且證據（change 位置、範圍、commit 或 pending）經核對確認後**，補上轉換紀錄／承接對照 metadata | **不執行承接流程**，不憑空凍結範圍、不宣布 change 存在；資料缺漏先釐清，不補猜測內容 |
| 快照 | 建議選用的 `history/` 全文快照 | 快照路徑、唯一識別、版本與來源；由使用者決定是否保存，不自動建立，不覆寫既有快照 |

建立**新**的正式輸入目錄不在上述操作內：那屬於流程 B 的步驟 5、6，由人與代理依手冊手動處理。

### 完成時的回報

結果（`reuse`／`new`／`continue-change`／`needs-clarification`）、主稿路徑、本次範圍、修訂或關係記錄、證據與 pending 項目、尚未釐清的事項與下一個適用階段；不冒稱需求已正式確立或後續階段已被更新。
