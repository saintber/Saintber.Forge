# ADR-0002：遷移交付範圍與後續需求的確立方式

- 狀態：Accepted
- 日期：2026-10-07
- 核准者：`saintber`（使用者本次明確指示）
- 關聯：[ADR-0001](0001-hub-and-project-split.md)、[採納時的設計快照](0001-attachments/design-2026-10-adopted.md)

## 背景

設計快照描述 Hub、Tool、Shared 的方向與預期前景，但細節原本預計在後續開發時再討論。遷移審閱逐漸把「補齊快照中所有功能」當成交付條件，超出了這次收尾目的。

使用者已明確決定：本次以遷移完成為目標；已開始的 Spec Kit 擴充整理成可交付狀態；尚未完成的功能列為後續事項，不再擴大開發。必要驗證、文件與提交完成後結束，不安排第二階段。

## 決策

### 1. 本次只完成遷移與已開始工作的交付

- 完成已有內容的目錄遷移、治理與文件整理，以及必要的驗證和提交。
- 已開始的 Spec Kit 擴充，只交付已實作並驗證的能力；修正會損失內容、覆蓋使用者修改、錯誤採納或錯誤回報完成的缺陷，是交付前的必要工作。
- 未完成的功能明確記為後續事項，不再因設計快照曾列出它，就在本次新增實作。
- 自動 Policy Check、編號流程強化與尚未驗證的完整代理流程，若本次未完成，就保留其限制與證據，不宣稱已交付。
- 本次不展開 saintber CLI、bootstrap、工具入口、發佈流程或其他後續功能，也不安排第二階段。

### 2. 設計快照提供方向，不是完整且正確的詳細需求

- 快照保留原樣，用來理解前景、責任邊界及討論歷史。
- 不得直接把整份快照轉成後續必須實作的需求或任務，也不得以「忠實展開設計」代替需求討論與驗證。
- 已批准的憲章、治理規則與明確決策仍依其核准範圍適用；本決策不把既有治理全部撤銷。後續 change 必須檢視適用的 Policy，發現不足或衝突時，依既有修訂程序處理。
- 這項定位也適用 Spec Kit 擴充；本次工作包只描述本次實際交付的範圍。

### 3. 後續開發逐項以 Spec Kit change 討論

1. 依使用者要處理的問題開啟新的 change，確認目標專案。
2. 讀取現行有效規格、憲章與適用的 Policy；設計快照作為方向參考。
3. 討論詳細需求、限制與驗收條件，在該 change 的 spec、plan、tasks 確立本次範圍。
4. 依本次確立的設計實作與驗證，再依適用的採納、封存流程收尾。

後續事項清單只是未來需求討論的入口，不代表已批准實作、排定順序或承諾時程。

### 4. 優先交付可供 worktree 並行開發的目錄基準

使用者於 2026-10-07 補充：先完成主要遷移與基本目錄、文件、驗證、提交，讓後續各章節可以從提交基準開出 worktree；Spec Kit 擴充設計的確認不阻擋遷移。

- 固定 Hub 的程式、測試、文件、Script 與開發工具位置；尚無功能的目錄以責任說明或占位檔追蹤，不虛構功能。
- 提供 Tool 目錄範本，供實際開始開發時使用；尚未開發的工具仍只列規劃，不預先登錄成可用專案。
- 已開始的擴充保留程式、測試、工作包與待審設計，完成必要安全修正與驗證；不因遷移完成就宣稱完整擴充已採納或設計已定案。
- 小粒度的 skill 等工作可以直接開發、驗證與提交，**不強迫一律建立 Spec Kit 工作包**。適用的憲章、Policy、規格唯一及設計先於實作仍須遵守；涉及已採納規格的變更仍要有相應驗證與採納紀錄，不把自動擴充當成並行開發的前置依賴。

這是 owner 本次明確指示，補充現有工作流程對 Spec Kit 的使用範圍；不排第二階段。

## 影響

- 原本因設計快照而要求本次補齊的未完成功能，改為明確的後續事項；這是 owner 的本次裁決，不是代理自行縮減範圍。
- 遷移完成與「快照描繪的所有功能完成」分開判定；交付文件保留已知限制與未驗證範圍。
- 本決策補充並限縮 ADR-0001 的遷移交付解讀，不重寫快照，也不更改其他既有明確決策。
- 進度與本次證據見 [遷移狀態](../../migration-status.md)。
