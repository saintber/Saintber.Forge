# Invocation Contract

> 目的：規範 **Hub 與工具之間的呼叫契約**。約束 saintber 與透過它發佈、呼叫的工具**雙方**；每條規則標示適用角色：`[hub]`、`[tool]` 或 `[hub, tool]`。
> 本文是對**已採納設計 §7、§8** 的忠實展開。**目前 saintber CLI 尚未實作**，所以這份契約是**尚待實作去遵守的設計**，不是已存在的行為（憲章原則 VII）。實作時，**契約要先於實作被審查**；格式（schema）也不得依已偏離的程式反推（憲章原則 VI）。
> **不包含**未核准的條件：不規定發佈的觸發方式、不規定 CI 的檔案系統權限、不規定 pack 是否一律需要憑證。

## 規則

### R1 `[hub, tool]` 自主與互不知道內部（憲章原則 I、III；§1.3）
- 工具可以被**直接呼叫**，也可以經由 Hub 委派；**兩者走同一套實作與同一份狀態**。
- Hub 只知道「工具在哪裡、怎麼呼叫」；工具只知道「收到什麼操作與參數」。

### R2 `[hub]` 路由（§7.1、§7.3）
- 命令前綴必須**唯一**；拒絕有歧義的重疊前綴，避免新增工具時改變既有命令的歸屬。
- 前綴**不得**與 Hub 自身的命令名稱（`list`、`info`、`status`、`profile`、`cache`、`alias`、`self-*`、`doctor`）重疊。
- Hub 解析出前綴後，把**剩下的參數原樣交給工具**；工具內部的子命令不由 Hub 逐一註冊。
- 純分類群組（例如 `ai`）只用來導覽，**不虛構**安裝或執行行為。

### R3 `[tool]` 操作（§7.1、§7.4、§8.1）
- 每個可操作的工具至少提供 **install、configure、run**；**強烈建議**提供 `status`。
- 每個可操作的子項目提供自己的 install / configure / run；`update` / `uninstall` / `doctor` 依需求宣告。
- 工具在 manifest 宣告公開入口、支援的契約版本與操作。manifest 只描述**公開入口與呼叫契約**；工具內部的資料放 `toolMetadata`，Hub 不解讀。
- 工具自己決定安裝範圍、位置、狀態與 PATH；工具資料**不假設**放在 Hub 家目錄（§8.2、§8.4）。

### R4 `[hub]` 參數與工作目錄（§7.3）
- 以**參數陣列**啟動子程序，**不拼接 shell 字串**；保留參數的順序、空白、引號內容與 Unicode。含空白或 Unicode 的路徑是合法的，契約保證能正確傳遞，**不以禁止這類路徑代替**。
- Hub 自己的選項只能放在工具前綴**之前**；前綴之後的一律屬於工具。
- 保留使用者執行命令時的**工作目錄**；入口包的位置另外用絕對路徑解析，**不會**把工作目錄切到快取目錄。

### R5 `[hub, tool]` 環境、stdio 與結果（§7.3）
- 環境變數**原樣傳遞**。Hub 只額外提供契約明定的少數資訊；工具**不得**依這些資訊改變業務行為 `[tool]`。
- 預設直接**繼承** stdin / stdout / stderr，讓工具自行做互動詢問；是否支援非互動模式由工具宣告。契約只保證「繼承」，Windows 與 Linux 的 TTY 細節**待驗證**。
- **原樣回傳**工具的退出狀態，不改寫，也不要求工具避開任何數值。由於任何工具都可能回傳和 Hub 相同的數值，**不能只靠退出碼判斷錯誤來源**：Hub 自身的錯誤在 stderr 加上 `saintber:` 前綴，需要機器判讀時提供結構化輸出的來源欄位 `[hub]`。
- Hub 收到取消時**轉交**給子程序並等待它結束 `[hub]`。子 CLI 結束**不代表**它啟動的長期服務已經停止，服務的生命週期由工具管理 `[tool]`。Windows 與 POSIX 的訊號語意不同，實際行為**待驗證**。

### R6 `[hub]` help 與版本（§7.3）
- `saintber --help` 只說明 Hub 命令與工具清單；工具前綴之後的 `--help` 交給工具。
- 入口包的版本與工具本體的版本**分開**；Hub 不會因為取得新的入口包，就默默變更已安裝的工具。

### R7 `[hub, tool]` secret（§7.3；POL-SEC-001 R4）
- secret **不建議放在 argv**（行程清單看得到）。
- 工具在 manifest 宣告支援的傳遞方式（環境變數、stdin、檔案路徑）`[tool]`；Hub **原樣傳遞，不記錄、不快取** `[hub]`。

### R8 `[hub]` 狀態：Hub 不持有工具的安裝狀態（§8.3；ADR 決策 4）
- 工具的安裝狀態**只由工具自己保存**。工具可以被直接安裝，所以 Hub **不能**用「沒有經過 Hub 安裝」判定工具未安裝。
- 狀態以工具公開的 `status` 為準；工具沒有提供、尚未取得入口包、或查詢失敗時，顯示為 **`unknown`** 並附上原因。
- `list --installed` 只是對每個工具執行 status 後彙整，**不假裝知道所有工具的狀態**。

### R9 `[hub]` 入口的取得（§7.5、§7.6）
- Hub 依 catalog 中**公開的來源描述**取得入口包，**不從 tag 猜測子目錄**，也不理解工具內部的建置方式。
- 來源類型：`release`（優先）、`git`（必須寫明 repo、**固定 commit**、入口根目錄、manifest 位置；`prepare` 必須是工具公開宣告的包裝指令）、`local-dev`（只用於開發）。
- `prepare` 的工作目錄是隔離取得的 `entryRoot`，只有 `prepare` 使用；委派 install / configure / run 時仍用使用者的工作目錄。
- 入口 runtime 與工具本體 runtime **分開**（§7.5）。入口 runtime 不存在、又沒有 bootstrap wrapper 時，Hub **明確報錯**並列出前提，**不會**變成所有 runtime 的通用安裝器。

### R10 `[hub, tool]` 工具之間的前置需求（§8.5）
- `requires.tools` 只是**資訊**；Hub 不自動排序或安裝前置工具。
- 實際檢查由工具透過前置工具的**公開 CLI** 進行，不讀對方的內部檔案。

### R11 `[hub]` Hub 自身的邊界（§8.2、§9.3、§9.5）
- Hub **不注入**統一的安裝範圍、不補預設目錄。
- Hub 只操作**自己明確持有**的項目；`cache clean`、`self-move`、`self-uninstall` 遇到非 Hub 的內容時保留並提示。所有權**不會往下繼承**。
- `cache clean` **不是** uninstall；`self-uninstall` **不會**移除任何工具的本體、設定或資料。

## 尚未決定的事項（不是規則）

下列在採納設計中標為**待驗證或落地時決定**，**不在本契約的範圍**：
- Windows 與 POSIX 在 TTY、取消訊號上的實際行為。
- Hub 自身退出碼的配置、契約提供的環境變數清單。
- Windows / Linux 平台矩陣之外的平台（macOS、Windows arm64）。
