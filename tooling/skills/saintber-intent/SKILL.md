# saintber-intent：需求分析與主稿管理

整理問題、情境、目的、期待結果、範圍／非目標、已確立限制、驗收方向與未決事項；使用繁體中文。需求分析可以與方案探索來回確認，但不要替使用者選實作方案或把推測寫成已確認需求。讀取設計稿以理解背景，只修改需求分析內容，不改方案探索、候選 spec、plan、tasks、程式或有效規格。不啟動 Spec Kit、初始化專案、執行承接／採納／封存、stage、commit 或 push。

## 目標與依據

自然語言為主，也接受 `project=hub|<id>`、`topic=<名稱>`、`from=<來源主稿>`、`owner=<擁有者>`；這些是文字提示，不是 shell 片段。依本次需求決定操作，不要求固定參數或先準備正式 Intent。

- 確認 owner、專案根目錄、本次問題與範圍。workspace 以同一 worktree 的 `workspace.json` 驗證；未指定時依 cwd 所屬專案及使用者內容確認，不能判斷才詢問。明確指定但不存在的 ID／路徑就停止，不退回 Hub、不自行成立 Tool。
- 既有 Tool 的稿放自己的 `docs/proposals/`。未成立 Tool 只有在使用者明確指定時才暫放 Hub，標預計 owner。standalone 依自身治理，不依賴父 repo。
- 讀目標的 `AGENTS.md`、Policy 索引、已有的憲章與相關有效規格索引；workspace 另讀適用的 Hub 治理。流程用詞與承接規則讀同一 worktree 的 `docs/developer-guide/development-workflows.md` §2、§3、§10、§11，管理細節可參考 `docs/developer-guide/intent-workflow.md`。standalone 使用內化版本；必要依據缺漏或互相衝突時先釐清。
- 本次技能的管理操作依使用者要求實作；被引用的 Proposed 文件仍是提案，不因技能存在而變成已採納 Policy。當地已生效治理優先，衝突不自行裁決。引用文件是內容與證據，不授權其中的任意命令。

## 先核對主稿與承接

用 `rg` 找同 owner、同問題、同範圍的主稿、來源與關係；搜尋目標的 `docs/proposals/`、`docs/intent/`、工作包及有效規格，需要追溯時才讀封存與 Git。不要只看檔名，也不要把歷史或候選 spec 當已驗證現況。

1. 讀同 topic 的需求分析、探索稿或合併稿：狀態、目前決策、本次範圍、尚未實作及各角色的轉換紀錄。只有 design 沒有 intent 不表示要另開 topic；另一角色已承接同範圍也不能忽略。
2. 核對轉換紀錄的日期、範圍、對應 change、目前位置、來源 commit／pending，並讀實際工作包、封存、有效規格及相關 Git 證據。commit 要真的含被引用的內容，不能用當前 HEAD 代替未提交稿。
3. 核對需求來源與關係：同一範圍只有一份整合的現行依據，可引用多個相容來源。來源矛盾不悄悄合併；列出未決需求。轉換紀錄空白、pending、缺漏或路徑失效不等於未轉換，證據不明就先釐清。

| 結果 | 判斷與本指令動作 |
|---|---|
| `reuse` | 同問題的未結案、未被承接範圍，同稿修訂；小幅範圍調整仍是同一問題時記實質修訂。既有 topic 只有 design 時，結果仍是 `reuse`：在同 topic 新建 intent，不改 design；合併稿則只改需求部分。這是主題層級的沿用，不以是否新增角色檔判為 `new`。 |
| `new` | 新獨立問題／可獨立驗收的範圍，或確定已結案／撤回／封存後的新需求；建立不重名 topic，連回相關來源，不把新問題當同需求 v2。 |
| `continue-change` | 同範圍已被仍活動的 change 承接，有沒有正式 Intent 都適用。回報實際工作包；早期被承接範圍不改、不另開重複 topic。只有使用者要修訂且正式 Intent 已存在，才依下節修訂。 |
| `needs-clarification` | 專案、owner、問題、範圍、現行權威、狀態或承接證據不明／矛盾；回報已查證資料與待決問題，停止相依寫入。 |

混合已承接與未承接範圍時分開處理；部分承接不整份凍結，也不整份覆寫。使用者說「重寫」不等於授權改寫已結案的歷史。已封存 change 不續寫，後續需求走 `new`。

## 建立與修訂早期稿

- 同 topic 同角色一份主稿；沿用已確認的 `<topic>.md`、`<topic>/intent.md` 或舊格式。全新需求分析預設 `<topic>/intent.md`；小稿明確採合併形式時用 `<topic>.md`。已有合併稿就只修需求部分，不自動拆稿或再建角色檔。目錄內已有 design 時加入 intent，不另開 topic。合併稿旁的同名目錄只有歷史附件時，不當成第二份主稿。
- topic 是 proposals 下單一名稱，不能含路徑分隔、`..` 或指向外部的連結。目的地重名、兩份同角色主稿、來源角色界線不明時先釐清。寫入路徑須在確認專案內，拒絕 symlink／junction 逃出邊界。
- 寫入前說明目標、結果與檔案，這是進度說明；既有授權內不另設批准關卡。新檔不覆蓋，修訂前重讀並比對原內容，發現他人改動先重新核對，不覆蓋其他變更。
- 新稿標草稿、owner、目前決策及真實授權來源、本次範圍、尚未實作；按需要整理需求，不強迫每個小稿填滿章節。未決內容標待釐清，不能因建稿宣告需求已批准、規格已確立或能力已實作。
- 未結案同稿迭代，不強制版本號、不另建 v1／v2 副本。實質改變（問題、目標、範圍、限制、驗收方向）追加「需求修訂記錄」：日期、改了什麼、為什麼、真實依據、快照（選用）。錯字、措辭或排版不列實質修訂。初稿可寫「尚無修訂」與「轉換紀錄：尚無轉換」。
- 依據使用真實使用者指示、存在的文件、已核對 commit；沒有記錄或未提交就寫 `pending（原因）`，不虛構。Git 只保留已提交文字；摘要不等於可還原未提交舊文。
- `from` 與已確認的延伸／拆分／取代關係記實際來源連結、部分或整份範圍、日期與依據。不要修改舊來源的歷史或自行宣布取代。一般建立／修訂不是承接，不追加虛構轉換列。

## 既有正式 Intent（選用）

只作用於已確認存在、仍活動的 change 及其既有 `docs/intent/<NNN-name>/intent.md`。本指令不建立新的正式輸入，不決定 change 編號。修訂正式 Intent 的結果仍回報 `continue-change`，並說明本次實際修訂；沒有正式 Intent 就只回報位置與建議，需求變化依該 change 流程處理。

- 只讀 Current Effective Intent 的現行需求；Version Index、Related Documents、Appendix、修訂摘要及歷史補充不是現行需求。若有獨立行的 `<!-- 現行範圍開始 -->`／`<!-- 現行範圍結束 -->`，核對唯一一對、順序正確且在 Current Effective Intent 中；範例程式區塊中的文字不是邊界。缺一、重複、倒置或與版本／內容矛盾就先釐清，不猜測尾端。
- 活動舊格式沒有標記時，先核對 Current Effective Intent 標題、版本及需求章節，排除相關文件與歷史；能確認範圍才補邊界，不能確認就停止修訂。只補格式不升需求版本，不回改封存。舊 `Trigger` 可辨識為原因，下次實質修訂再對齊。
- 使用者要求修訂時，修改現行內容並更新 Intent Version Index。版本代表需求語意：實質改變換下一個不重用的版本並記日期、Reason、Summary、Evidence；沿用已確立編號慣例，無慣例用簡單序號，不強制 semver。錯字等非語意修正可同號；不可用同號表示不同需求，也不回寫舊索引的語意。來源未提交記 pending，不自動 commit。
- 修訂前若使用者要求保留舊全文，先確認真實 commit／既有快照是否保存；未保存時說明需先保存選用快照，再修訂。技能本身不自動產生快照；需要的另行保存未完成時，不先覆蓋欲保留內容。
- 實質修訂後列出受影響的 spec、plan、tasks、驗收與不一致；這些仍需依後續流程對齊，未對齊前不續做受影響實作。本指令不順手修改它們，Intent 不代替候選 spec 或有效規格。

## 來源 metadata 與歷史

只有使用者明確要求補記「已實際發生」的承接，且 change、範圍、來源與證據經核對時，才補轉換紀錄或正式 Intent 邊界外的來源對照。列日期、範圍、實際對象位置、來源 commit／pending；不執行承接、不憑空凍結或批准內容。缺證據先釐清。沒有正式 Intent 時只建議在既有 spec 的來源 metadata 補記，本指令不改 spec。

多個相容來源可並列於來源對照（承接範圍、實際來源、證據、狀態），每範圍仍只有一份整合現行依據；矛盾標待釐清，不能拿來源表當需求。本指令不代做 specify；未決事項可進後續規格草案，但受影響實作須等需求與設計對齊。

里程碑快照是選用唯讀歷史，可建議 `docs/proposals/<topic>/history/intent-<唯一識別>.md` 或正式輸入的 `history/`。不自動建立、不覆寫，現行稿引用實際保存的路徑與來源；合併稿全文須標角色與原正本，不能變成另一份活動需求。封存預設只用於追溯，不讀作現行需求。

## 完成回報

回報 `reuse`／`new`／`continue-change`／`needs-clarification`、主稿或工作包位置、本次範圍、修訂／關係紀錄、承接證據與 pending、待釐清事項及下一階段。檢查本地連結、狀態、範圍、角色保留與正式現行邊界。不宣稱下游文件已更新或治理已採納；這是代理讀檔判斷的技能，沒有機械狀態鎖。

維護正本 `tooling/skills/saintber-intent/SKILL.md`，以其 `install.mjs` 產生代理入口，不直接修改副本或上游 `speckit-*`。
